Two prefixes that are easy to confuse

wal-text-* sets a font size. wal-color-* sets a colour. There is no .wal-text-muted class — --wal-text-muted is a token, and the class you want is .wal-color-muted. Using the token name as a class fails silently, which is how the previous version of this page ended up applying roughly twenty rules that did nothing. 

<p class="wal-text-sm wal-color-muted">small and muted</p>

<!-- does nothing: .wal-text-muted is not a class -->
<p class="wal-text-muted">still full size, full contrast</p>

Tokens

Five hue rods generate the palette

Every colour is derived in oklch() from a handful of numbers, so retheming is arithmetic rather than a second stylesheet. 

:root {
  --wal-hue: 55;             /* surfaces and text   */
  --wal-chroma: 0.04;        /* how warm they are   */
  --wal-accent-hue: 25;      /* terracotta          */
  --wal-gold-hue: 85;        /* goldenrod           */
  --wal-olive-hue: 130;      /* botanical green     */

  --wal-accent-chroma: 0.17; /* saturation, per rod */
  --wal-gold-chroma:   0.15;
  --wal-olive-chroma:  0.10;
}

The chroma tokens exist because the sRGB gamut is not the same width at every hue. At 62% lightness c=0.17 sits in gamut around terracotta and clips across much of the green–blue arc, where the browser flattens it silently and the rendered colour stops matching the hue you asked for. So if you rotate a hue rod at runtime, lower its chroma with it. CSS cannot compute the gamut boundary, which is why this is an input rather than something walnut can guard for you.

Palette

Themes

Palette travels by class, light/dark travels by attribute. They are separate axes, so they compose — and a selector like [data-theme="cafe"][data-theme="light"] can never match, because an element has one value per attribute. 

<html class="wal-cafe"   data-theme="dark">   <!-- café, dark   -->
<html class="wal-forest" data-theme="light">  <!-- forest, light -->
<html data-theme="bone-light">                <!-- fused form    -->

Palettes: wal-cafe, wal-forest, wal-dusk, wal-bone. Omit data-theme and the system preference decides.

Utilities

Layout and type helpers

Grid

.wal-cols-* sizes intrinsically with auto-fit over a minmax() floor. It needs no container query, so it collapses correctly at any nesting depth — including inside a card or a sidebar. 

<div class="wal-grid wal-cols-3">…</div>   <!-- 16rem floor -->

Cascade

Your CSS wins by default

walnut ships entirely inside @layer. Unlayered declarations beat every layered one regardless of specificity, so an ordinary rule of yours overrides the framework with no !important and no specificity games. 

@layer wal.reset, wal.tokens, wal.base, wal.layout, wal.components, wal.utilities, wal.cinema;

/* unlayered — beats all of the above */
.wal-card { border-radius: 3px; }

Two caveats worth knowing before you debug one of them. An unlayered rule only outranks the framework for the properties it actually declares — override flex-direction and walnut's gap still applies. And !important inverts layer order, so walnut's reduced-motion block deliberately still wins.
